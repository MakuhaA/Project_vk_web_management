# Задание №1 
## Проект: Вайб рядом

**Выбери настроение - найди место с атмосферой.**
 
**Бизнес-модель:** B2C + B2B.  

### Описание проекта

«Вайб рядом» специализируется на атмосферных прогулках: романтических, уютных, эстетичных или спокойных. Пользователь выбирает настроение, район, доступное время и бюджет, затем нажимает «Удиви меня». Сервис случайно предлагает подходящее место из каталога, прошедшего модерацию: уютную кофейню, парк, набережную, красивый дворик, выставку или творческую студию. Для каждой локации важно, какое настроение и впечатление она создаёт.
Случайный выбор происходит среди опубликованных мест, подходящих под настройки пользователя. Для каждого места доступны фотография, описание атмосферы, адрес, режим работы и информация о стоимости посещения. Бесплатные локации входят в каталог наравне с платными.
Пользователи могут бесплатно предлагать собственные находки и делиться ими с другими: добавлять фотографии, адрес, описание атмосферы и подходящие настроения. Каждая заявка сначала проходит модерацию. После одобрения место появляется в общем каталоге и может участвовать в подборе; в карточке указан автор находки.
Дополнительно можно купить прогулку-сюрприз из нескольких остановок с подсказками и небольшими заданиями. Кафе и другие заведения могут оплачивать размещение и продвижение, чтобы привлекать посетителей через сервис.

### Elevator Pitch

«Вайб рядом» - проект для атмосферных прогулок: романтических свиданий, уютных встреч и времени для себя. Пользователь выбирает настроение, район и бюджет, а сервис случайно предлагает подходящее место или прогулку-сюрприз. Каталог пополняют сами пользователи: они делятся любимыми местами, фотографиями и впечатлениями, а публикации проходят модерацию. Подбор отдельных мест и добавление своих находок бесплатны. Приложение зарабатывает на продаже авторских прогулок и платном продвижении кафе, творческих студий и других заведений. Пользователи открывают места с нужной атмосферой и делятся ими с сообществом, а заведения получают возможность привлечь заинтересованных посетителей и отслеживать отклик.

### Бизнес-модель

**B2C:** пользователи оплачивают прогулки-сюрпризы из нескольких остановок с подсказками и заданиями.

**B2B:** кафе, творческие студии и другие площадки оплачивают продвижение своих одобренных карточек среди подходящей аудитории. Платные размещения обозначаются как «Партнёрское место».

# Задание №2
## Основные риски по Марти Кагану

**Основной риск** - риск ценности: пользователи могут оказаться не готовы платить за подготовленные атмосферные прогулки, а заведения - за продвижение среди аудитории приложения.

Разделим гипотезы для пользователей и для заведений.


## HADI 1 - готовность пользователей покупать маршруты

### H - гипотеза

Предполагаем, что не менее 5% представителей целевой аудитории, увидевших предложение с ценой, купят атмосферный маршрут за **200 ₽**.

### A - действие

За 14 дней проведём пилот в одном городе. Создадим веб-страницу с примерами прогулок, проверенными местами, условиями получения маршрута и возможностью оплаты. Привлечём аудиторию через социальные сети.

В пилоте допустима ручная подготовка маршрутов. Будем учитывать время этой работы в расходах на выполнение заказов.

### D - данные

Соберём количество уникальных посетителей, увидевших предложение с ценой, нажатий на кнопку покупки, уникальных покупателей и возвратов.

**Конверсия в покупку = количество покупателей / количество посетителей, увидевших предложение × 100%.**


### I - критерий будущего вывода

Если предложение увидят минимум 200 целевых посетителей и конверсия составит не менее 5%, гипотеза получит предварительную поддержку. При 200 посетителях это минимум 10 покупателей.

Это сигнал готовности платить для выбранного города, предложения и цены. Для проверки повторных покупок продолжим наблюдение за этой группой клиентов.

При конверсии ниже 5% изучим причины отказов и проверим обновлённое предложение. При выборке меньше 200 посетителей данных для решения по выбранному критерию будет недостаточно.

## HADI 2 - готовность заведений оплачивать продвижение

### H - гипотеза

Предполагаем, что минимум 3 из 15 подходящих заведений, получивших конкретное предложение, оплатят первый месяц продвижения за **1 500 ₽**.

### A - действие

После пользовательского пилота за следующие 30 дней предложим размещение 15 кафе или творческим студиям в том же городе.

Покажем фактический размер аудитории, пример партнёрской карточки, условия размещения и доступную статистику. Будем фиксировать показы карточек, переходы и обращения. Визиты или покупки учитываем только при наличии подтверждения.

### D - данные

Зафиксируем число заведений, получивших предложение, устные согласия, фактические оплаты, причины отказов и затраты на продажи. После размещения будем отслеживать продления и расходы на обслуживание.

### I - критерий будущего вывода

Если минимум 3 из 15 заведений оплатят первый месяц, гипотеза получит предварительную поддержку для этого предложения и выборки.

При меньшем количестве оплат пересмотрим цену, условия или ценность размещения. Для проверки предположения о шести оплаченных месяцах будем наблюдать за продлениями в течение шести месяцев.

## Расчёт CAC и LTV

В расходы включаем рекламу, материалы и работу по маркетингу и продажам. Расходы связываем с привлечёнными клиентами с учётом длительности продажи. Общие затраты распределяем между направлениями один раз.

### Допущения и расчётный сценарий

| Показатель | Пользователи | Заведения |
|---|---:|---:|
| Расходы на привлечение за соответствующий пилот | 5 000 ₽ | 3 000 ₽ |
| Новые платящие клиенты в сценарии | 10 | 3 |
| Цена одной оплаты | 200 ₽ за маршрут | 1 500 ₽ за месяц |
| Переменные расходы | 40 ₽ на покупку | 300 ₽ в месяц на заведение |
| Ожидаемые оплаты за весь срок сотрудничества | 4 покупки | 6 месяцев |
| CAC | 500 ₽ | 1 000 ₽ |
| LTV по выручке | 800 ₽ | 9 000 ₽ |
| LTV | 640 ₽ | 7 200 ₽ |
| LTV / CAC | 1,28 | 7,2 |

При оценке затрат учитываем комиссии, подготовку маршрутов, модерацию, поддержку и другие расходы, зависящие от заказов и клиентов. Время команды оцениваем по заранее выбранной ставке.

Разработка, постоянные расходы и налоги в этом упрощённом расчёте отдельно не учтены.

### Пользователи

- CAC = 5 000 / 10 = **500 ₽**.
- LTV по выручке = 200 × 4 = **800 ₽**.
- LTV = (200 − 40) × 4 = **640 ₽**.
- LTV/CAC = 640 / 500 = **1,28**.

### Заведения

- CAC = 3 000 / 3 = **1 000 ₽**.
- LTV по выручке = 1 500 × 6 = **9 000 ₽**.
- LTV = (1 500 − 300) × 6 = **7 200 ₽**.
- LTV/CAC = 7 200 / 1 000 = **7,2**.

### Целевой ориентир

Для проекта принимаем **LTV/CAC ≥ 3** как золотое правило. Окончательный вывод зависит также от постоянных затрат, сроков поступления денег и устойчивости спроса.

Пользовательское направление при текущих допущениях остаётся ниже цели. Проверим способы снизить CAC через более точное продвижение, рекомендации пользователей и улучшение конверсии.

При цене 200 ₽, расходах 40 ₽ на покупку и четырёх покупках:

- предельный CAC для цели ≥ 3 составляет 640 / 3 ≈ **213 ₽**;
- при бюджете 5 000 ₽ нужны минимум **24 новых покупателя**: CAC ≈ 208 ₽, LTV/CAC ≈ 3,07;
- при CAC 500 ₽ потребовалось бы в среднем **10 покупок** за срок жизни клиента: (200 − 40) × 10 / 500 = 3,2.

Это условия достижения цели. То есть либо уменьшаем расходы, либо увеличиваем количество покупок.

## Сводная экономика двух направлений

Для расчётной группы из **10 пользователей и 3 заведений** можно получить взвешенные средние показатели.

**Средний CAC = (5 000 + 3 000) / (10 + 3) ≈ 615 ₽.**

Ожидаемый маржинальный доход за срок сотрудничества:

- пользователи: 10 × 640 = **6 400 ₽**;
- заведения: 3 × 7 200 = **21 600 ₽**;
- всего: **28 000 ₽**.

**Средний LTV = 28 000 / 13 ≈ 2 154 ₽.**

**Сводный LTV/CAC = 28 000 / 8 000 = 3,5** <- Золотое правило выполняется

## 2. MVP

**MVP** - минимальная версия для проверки готовности пользователей покупать маршруты, а заведений - оплачивать продвижение.

В MVP входят:

1. Выбор настроения, района, времени и бюджета, получение случайного подходящего места - **User stories 1–2**.
2. Предпросмотр маршрута, оплата 200 ₽ и получение доступа - **User story 3**.
3. Повторный доступ к отдельной покупке по защищённой ссылке с восстановлением через подтверждённый email.
4. Отправка пользовательских мест и модерация перед публикацией - **User story 6**.
5. Создание карточки заведения, просмотр результата модерации и оплата продвижения за 1 500 ₽ - **User stories 11–13**.
6. Маркированные партнёрские рекомендации и базовая статистика размещения - **User story 14**.

Маршруты заранее подготавливаются, модерация выполняется вручную. Оплата и предоставление доступа обрабатываются системой.

Обновление опубликованной карточки и продление продвижения в пробной версии — через поддержку.

## 4. Требования к двум основным задачам

### Общие требования

- Сервис доступен всё время.
- Защищённая передача данных.

### 4.1. Задача пользователя

**Найти атмосферную прогулку и купить подготовленный маршрут за 200 ₽.**

Связанные истории: **User stories 1–3**.

#### Функциональные требования

| № | Требование |
|---|---|
| 1 | Система позволяет указать настроение, район, время и бюджет. Местоположение можно задать вручную. Рекомендации доступны без регистрации. |

| 6 | Надёжность | Оплаченные заказы доступны для повторного использования. |

### 4.2. Задача заведения

**Разместить карточку и запустить продвижение за 1 500 ₽ в месяц.**

Связанные истории: **User stories 11–14**.

#### Функциональные требования

| № | Требование |
|---|---|
| 1 | У заведения есть доступ к разделу своей карточки через подтверждённый email. |
| 2 | Система позволяет создать карточку со всей информацией для пользователей: названием, категорией, адресом, фотографиями, описанием атмосферы, временем работы, ценовым диапазоном и контактной ссылкой. Обязательные поля проверяются перед отправкой. |
| 3 | Карточка поступает на модерацию. Представитель заведения видит статус и замечания. |
| 4 | Перед оплатой система показывает тариф 1 500 ₽ за месячный период, даты размещения и условия показа. |
| 5 | После подтверждённой оплаты система активирует продвижение одобренной карточки. |
| 6 | Активная карточка может показываться в партнёрском блоке с учётом района, настроения и бюджета пользователя. |
| 7 | Представитель заведения видит показы, открытия карточки и переходы по контактной ссылке за выбранный период. |
| 8 | Система показывает статус и срок размещения. После окончания периода платное продвижение прекращается. Новое размещение требует отдельной оплаты. |

**Показ** учитывается при отображении не менее 50% карточки в активной вкладке минимум 1 секунду.

#### Нефункциональные требования

| № | Характеристика | Требование |
|---|---|---|
| 1 | Быстродействие | Операции сохранения карточки и открытия статуса завершаются максимально быстро; загрузка статистики — также быстро. |
| 2 | Разграничение доступа | Представитель изменяет только свои карточки и видит только свою статистику. |
| 3 | Надёжность учёта | Информация об оплате и период размещения сохраняются после перезапуска приложения. |
| 4 | Своевременность | Продвижение запускается и останавливается в пределах 60 секунд. Статистика обновляется каждые 3 часа. |
| 5 | Точность статистики | На контрольном наборе событий отчёт совпадает с ожидаемыми итогами показов, открытий и переходов. |
| 6 | Удобство | Представители заведения заполняют и отправляют карточку на проверку за 5 минут, имея готовые фотографии и описание. |

## 1. DDD: пять доменных зон

### Зона «Каталог мест»

Отвечает за сведения об атмосферных местах и показ опубликованных карточек.

| Термин | Значение в проекте |
| --- | --- |
| Место | Конкретная локация, которую можно посетить во время прогулки. |
| Карточка места | Информация о локации: название, фотографии, адрес и описание. |
| Тег настроения | Метка, которая описывает атмосферу места, например «уютное» или «романтичное». |
| Район места | Район или часть города, где находится локация, например центр. |
| Ценовой диапазон места | Ориентир по расходам на посещение места, например «бесплатно» или «до 500 ₽ на человека». |
| Ограничение по размеру компании | Условие заведения о количестве посетителей в одной компании, например «группа до 6 человек». |

### Зона «Маршруты»

Отвечает за подбор, предпросмотр и покупку маршрутов.

| Термин | Значение в проекте |
| --- | --- |
| Маршрут | План прогулки со списком мест в порядке их посещения. |
| Точка маршрута | Одно из мест, которое входит в план прогулки. |
| Предпросмотр маршрута | Краткая информация до покупки: тема прогулки, число точек и примерная длительность. |
| Индивидуальный маршрут | План прогулки, составленный по запросу пользователя с учётом его пожеланий. |
| Цена маршрута | Сумма за доступ к плану прогулки. В MVP готовый маршрут стоит 200 ₽. Расходы на посещение мест в эту сумму не входят. |

### Зона «Заявки на добавление мест»

Отвечает за отправку предложений от пользователей и отображение их статуса.

| Термин | Значение в проекте |
| --- | --- |
| Заявка на добавление места | Предложение пользователя добавить локацию в каталог, отправленное на проверку. |
| Автор заявки | Пользователь, который предложил место. |
| Данные заявки | Название, адрес, фотографии и описание атмосферы места, переданные на проверку. |
| Статус заявки | Текущее состояние заявки, по которому автор узнаёт, идёт ли проверка и какое решение принято. |

### Зона «Продвижение заведения»

Отвечает за платное размещение одобренных карточек и статистику их показов.

| Термин | Значение в проекте |
| --- | --- |
| Продвижение заведения | Платное размещение одобренной карточки в партнёрских рекомендациях. Стоит 1 500 ₽ за месяц. |
| Период размещения | Оплаченный срок, в течение которого карточка может появляться в партнёрских рекомендациях. |
| Партнёрский блок | Часть рекомендаций, где подходящие по фильтрам карточки с активным продвижением показываются с пометкой «Партнёрское место». |
| Показ карточки | Событие, которое засчитывается, когда не менее 50% карточки видно в активной вкладке не менее 1 секунды. |
| Открытие карточки | Переход пользователя к подробной информации о заведении. |
| Переход по контактной ссылке | Нажатие пользователя на контактную ссылку в карточке заведения. |

### Зона «Модерация»

Отвечает за проверку предложенных мест и карточек заведений перед публикацией.

| Термин | Значение в проекте |
| --- | --- |
| Модератор | Сотрудник сервиса, который проверяет заявки пользователей и карточки заведений и решает, можно ли их допустить к публикации. |
| На проверке | Заявка или карточка передана на рассмотрение. Решение ещё не принято. |
| На доработке | Модератор вернул заявку или карточку с замечаниями. После исправлений её можно отправить на проверку повторно. |
| Одобрена | Проверка пройдена. Карточку можно опубликовать в каталоге. |
| Отклонена | Заявка или карточка не соответствует критериям публикации. Модератор указывает причину отказа. |

## 2. BDD: покупка готового маршрута

- **Дано:** в каталоге опубликованы готовые маршруты с тегами, например «романтика», «активный отдых» и «уют». Пользователь подтвердил свою электронную почту.
- **Когда:** пользователь ищет прогулку для свидания и выбирает тег «романтика». Сервис показывает маршруты с этим тегом. Пользователь открывает предпросмотр понравившегося маршрута и оплачивает его за 200 ₽ через платёжный сервис.
- **Тогда:** после подтверждения оплаты сервис открывает полный план прогулки и отправляет на подтверждённую почту защищённую ссылку, по которой маршрут можно открыть повторно.

Историю покупок в аккаунте планируется добавить в будущих версиях.

## 4. API-ручки: покупка маршрута

### GET: предпросмотр маршрута

Клиент передаёт идентификатор маршрута в URL. Сервер возвращает данные, которые видны до покупки. Ниже указаны типы полей ответа.

```text
GET /api/routes/route_42/preview

200 {
  "title": String,
  "theme": String,
  "pointsCount": Int,
  "durationMinutes": Int,
  "priceRub": Int
}
```

### POST: создание заказа на маршрут

Клиент передаёт идентификатор выбранного маршрута. Сервер создаёт заказ и возвращает ссылку на оплату.

```text
POST /api/route-orders

{
  "routeId": "route_42"
}

201 {
  "orderId": "order_1024",
  "status": "pending_payment",
  "amountRub": 200,
  "paymentUrl": "https://pay.example/checkout/order_1024"
}

404 {
  "code": "ROUTE_NOT_FOUND",
  "message": "Выбранный маршрут недоступен."
}
```

Код `201` означает, что заказ создан и ожидает оплаты. Доступ к маршруту открывается после подтверждения платежа.

### 2. Стек технологий и обоснование для MVP «Вайб рядом»

**Веб-интерфейс: HTML, CSS и JavaScript**

- Один адаптивный сайт работает на телефоне и компьютере и содержит экраны для пользователей, представителей заведений и модераторов. JavaScript передаёт на сервер выбранные фильтры и отправляет запрос на создание заказа при нажатии «Купить».

**Backend API: Python + FastAPI**

- Один сервер обрабатывает заказы, заявки на модерацию и продвижение заведений. FastAPI проверяет данные запросов и автоматически формирует документацию API. В Swagger UI можно проверить работу `GET` и `POST`.

**База данных: PostgreSQL**

- Подходит для хранения связанных данных: маршрут состоит из нескольких мест, заказ связан с маршрутом и почтой покупателя, а у заявки есть автор и статус проверки.

**Обмен данными: HTTPS + JSON**

- HTTPS защищает данные при передаче, а JSON используется как формат обмена данными. Например, при создании заказа интерфейс передаёт идентификатор маршрута, а сервер возвращает сумму и ссылку на оплату.

**Приём платежей: внешний платёжный сервис**

- Пользователь оплачивает маршрут на странице платёжного сервиса, который обрабатывает реквизиты карты. Сервер «Вайб рядом» открывает маршрут после подтверждения оплаты.

**Отправка писем: внешний почтовый сервис**

- После оплаты почтовый сервис отправляет на подтверждённый адрес защищённую ссылку. По ней пользователь может повторно открыть купленный маршрут.
